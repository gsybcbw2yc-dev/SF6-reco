## 3. 取得経路・認証・勝敗とレーティングの根拠

1. 既存 `collector/collect.py` はすでに `/6/buckler/profile/{player}/battlelog/rank` のHTMLを取得していた。初回検証はこの既存レスポンスを再利用し、追加のBucklerリクエストなしで10試合、本人識別10件、replay_id10件、総ページ数10を確認した。
2. HTML内 `__NEXT_DATA__` の `buildId` と `locale` を毎回メモリ内で読み、総合履歴 `/6/buckler/_next/data/{buildId}/{locale}/profile/{player}/battlelog.json?page=N` を取得する。buildIdはハードコードせず、生レスポンスやCookieを保存しない。既存SecretだけでHTML・総合JSONの両方に認証できた。
3. 最初は2ページまで取り込み成功を確認してから、上限10ページへ広げた。追加ページ間は2秒。現在はソースが返す10ページ・約100件に制限し、11ページなどへの探索は行わない。初期走査完了後は既知の試合だけのページで停止する。
4. 本人識別は`player1_info.player.short_id`と`player2_info.player.short_id`で行い、ちょうど片側だけが対象IDと一致する場合に採用する。両側一致・どちらも不明なら取り込まず無効件数に数える。
5. 勝敗は両者の `round_results` を組で検査し、0＝敗北、1/2/3/5/6/7/8＝勝利方法、4＝引き分けという公開資料・先行実装の対応から派生判定する。未定義コード、空・長さ違い・矛盾する結果はunknown。これは原資料に独立した試合勝者フィールドがあるという意味ではなく、実リプレイ映像との全件照合は未実施。
6. MR・LPは公開技術資料での意味に従い「対戦前値」とする。対戦後値が検証できないので、前後試合の値差を確定した試合増減にしない。既存 `history.json` の観測差を各試合へ配分しない。
7. 勝率は `勝利/(勝利+敗北+引き分け)`。unknownは分母から除外。引き分けを半勝として数えない。少数の相手キャラを勝率だけで「苦手」と断定しない。

HTTP 401/403/429、認証リダイレクト、スキーマ変化では追加取得を止める。試合処理の失敗はMR/LP収集から分離し、安全な分類を `matches/status.json` に残す。後続ページだけが失敗した場合は取得済みの有効試合をpartialとして保存する。Buckler公開JSアセットをこの環境から読み取る試みは403で拒否されたため、その経路を再試行・迂回せず、勝敗コードの説明は下記技術資料と両者のラウンド情報に基づく実装として扱った。

## 6. データ構造・容量・通信・セキュリティ

月別保存はUTC月基準。`index.json`が月名、パス、件数、最初/最後の日時、バイト数、SHA-256を持ち、各`YYYY-MM.json`にschema 1の`matches`配列を保存する。日時欠損時はundatedとして扱う。indexは月ファイルを書いた後で更新する。

試合レコードはkey、occurred_at、time_basis、character、opponent_character、own_side、outcome、outcome_basis、mode、own_control、opponent_control、双方の対戦前MR/LP、phase、mr_delta/lp_delta、delta_basis、fetched_at、source、missingを持つ。keyは `SHA-256('sf6-reco:match:v1:' + replay_id)`。元のリプレイIDは公開しない。相手のCFN名・ユーザーIDも保存しない。初回の取得日時は走査開始付近の取得時刻を共有していたが、最終コードでは追加ページの受信時刻と走査完了時刻を分けて記録する。

`matches/status.json`はlast_success/last_attempt/last_errorと直近200件の安全な収集イベント。試合そのものを200件で間引く仕様ではない。古い試合アーカイブは保持される。全履歴のMR/LP観測は別ファイルのまま。

ブラウザは既存の60秒更新時にindex/statusを取得し、必要な月のハッシュが変わった場合だけ月ファイルを取得する。変更のない月を毎分再ダウンロードしないことを自動試験で確認した。通信不調時は前回の表示を保持する。

通常の成功収集は既存MR取得1リクエストと総合試合履歴1ページで合計約2リクエスト。初回は追加10ページ（総計最大11リクエスト）で、以降は既知ページで停止。25分ガードを通った収集だけで実行し、3つの画面のために別々にBucklerへ取得しない。MR取得時のランク10件も再利用するので、総合ページとの重複はキーで除外する。

現在100試合は約79KB。仮に100試合/日、1試合約800バイトなら約2.4MB/月・約29MB/年（予測値、実測ではない）。月1～2MBを超える場合は月内の不変チャンクへの分割を検討する。全期間を表示する際の読み込み・メモリも実機測定が必要。新しいサービス料金は発生していないが、GitHubの適用プラン・利用量・サービス側仕様が将来変わる可能性はある。

Cookieは既存Secretのみ。トークン・HTTP認証ヘッダー・生レスポンスをログ/JSON/報告書へ出さない。外部起動トークンの既知期限は**2026-12-08**。この新機能は追加の権限を要求しない。試合日時やキャラ・レーティングは公開サイトのデータとなる。
