# 長期履歴の容量・配信設計（2026-11-09）

現行 `web/data/history.json` は単一のJSON。収集成功時に毎回1キャラクター1観測値を保存する。00・30分の主系統が動けば最大約48点/日、1年で約17,520点/キャラクター。15件・4,594バイトだった時点の実測行平均を単純外挿すると約5.4MB/年/キャラクター（JSONの整形や追加フィールド次第で変化）。`runs.json` も別に増える。毎分ページを開き続けると年間履歴を毎回転送するため、端末の通信量と全期間グラフのDOM要素数が問題になる。

現時点では15件の公開履歴は小さく、月別分割の即時導入は不要。ただし履歴1MBまたは約3,000点を目安に配信時間・メモリ・端末通信量を測り、月別方式へ移行する。これは警告閾値であり、Pagesの正式な制限値ではない。

移行案：

1. `web/data/history-index.json` にschema、月別ファイル名、行数、UTCの最初・最後の観測時刻、ハッシュを記録。月の区切りはUTCで統一し、JST表示だけ画面で変換。
2. `web/data/history/2026-11.json` のように各月の観測値を保持。既存15件は時刻を変えず分配し、総件数・ハッシュで検算する。旧 `history.json` は移行中読み取り互換のため残す。新旧二重書きが必要な期間は同一取得で両者を更新し、差分検証をCIで行う。
3. ダッシュボードは7/30/90日に必要な月だけ取得。全期間は要求時に月別ファイルを取得し、表示用グラフは時刻範囲に応じて描画点を抑える。ただし計算・CSV/JSONエクスポートの生観測点は削除・推測・平均化しない。
4. 同一run/attempt/characterの観測IDで月内重複を防止し、GitHub Actionsの直列化とfetch/rebase/pushを維持。月境界では前月と当月を参照し、差分・フェーズ切替を判定。コミット失敗時は再読込して整合確認する。
5. `runs.json` も月別保存と最新24時間の軽量概要を検討。月別JSONの古い月は安定URLでキャッシュを利用し、当月とindexのみ毎分no-storeで確認。公開側で欠落月やハッシュ不一致を警告し、架空の観測値は作らない。

移行前後の回帰条件：旧全履歴の行数・時刻・MR/LP・フェーズの一致、重複IDなし、欠測保持、固定窓の計算結果一致、各月のPages HTTP 200、iPad Safariの読み込み速度と通信量の実測。現在は設計段階であり、月別JSONはまだ実装していない。
