# 試合・セッション・相性分析の運用

3画面は `web/data/matches/` の共通アーカイブだけを使う。MR/LPの定期観測 `history.json` と試合の対戦前レーティングは別データであり、一方の差を試合の確定増減に配分しない。

## 収集と切り戻し

`.github/workflows/collect.yml` の `MATCH_LOG_MODE=ingest` で、既存のMR/LP取得HTMLに含まれるランク履歴を再利用し、HTMLの `buildId` と `locale` から総合バトルログのNext.js JSONルートを組み立てる。初回は1ページの構造検証、次に2ページの実取り込みを確認した後、上限10ページに拡大。追加ページ間は2秒待つ。総合履歴で既知のページに到達すると差分取得を止める。初回2ページ時点の未取得範囲は `source_window_scanned=false` とし、その後の完全走査まで早期停止しない。

`MATCH_MAX_PAGES` は1～10。1ページ約10件、ソースが返す最大10ページの最近約100件に限る。取得間に100件超の新しい試合があれば取り逃す可能性があり、過去の未取得試合は復元しない。ページ番号の異常、スキーマ変更、HTTP 401/403/429や認証リダイレクトでは追加取得を停止。対戦履歴の失敗をMR/LP成功から分離し、`matches/status.json`へ安全な分類だけを記録する。後続ページ失敗時はすでに正規化できた試合をpartialとして保持する。

`MATCH_LOG_MODE=off` に変更すれば試合取得を無効化でき、既存MR/LP収集と保存済み試合は維持される。Cookieの更新は従来どおり `BUCKLER_ID` Secretで行い、コードやチャットには貼らない。既存の外部00/30分、予備11/41分、25分ガード、同時実行制御を維持する。

## 保存と公開範囲

- `index.json`: schema、総件数、月別ファイル名・件数・SHA-256・バイト数・最初/最後の日時、取得成功時刻、収集範囲の限界。
- `YYYY-MM.json`: schema 1、`matches` 配列。UTCの `uploaded_at` を月の区切りに使用。日時欠損は `undated.json`。
- `status.json`: last_success、last_attempt、last_error、安全な直近200件の取得イベント（run_id、ページ数、新規・重複・無効件数、停止理由）。
- `probe.json`: 初期検証の件数・スキーマ項目名だけ。本文や参加者識別情報は含めない。

各試合は生の `replay_id` を `SHA-256('sf6-reco:match:v1:' + replay_id)` に変換した安定キーで重複排除する。自分のCFN IDは1P/2P識別にだけ使い、相手名・相手CFN ID・生リプレイID・生レスポンス・Cookieはアーカイブへ保存しない。公開されるのは使用キャラ・相手キャラ・勝敗・モード・操作方式・対戦前MR/LP・アップロード日時・取得日時・欠損情報などである。

レーティングは原資料の数値を保持し、欠損はnull。`phase` は試合に明示された値だけを採用し、現在のプロフィールフェーズを過去試合へ付けない。明示値がなければunknown。月別JSONを書き、ハッシュ付きindexを最後に更新する。GitHub Actionsの直列化と最新main取得・push再試行で競合を抑制する。

## 計算の意味

日時は `uploaded_at`（アップロード日時）で、正確な試合開始時刻ではない。MR/LPはBucklerの対戦前値として扱う（参考資料の意味に基づく）。現在検証したレスポンスに対戦後MR/LPや確定増減の項目がないため、1試合・セッション・相性別の確定MR/LP収支は算定不可。

勝敗は両者の `round_results` を照合して派生判定。0が敗北、1/2/3/5/6/7/8が勝利方法、4が引き分けという公開クライアント関連資料・OSS実装の対応を用いる。不正なコード・空配列・両者の矛盾はunknown。実際のリプレイ映像との全件照合は行っていない。勝率は `勝利/(勝利+敗北+引き分け)`。unknownを分母から除外し、引き分けを半勝にはしない。

セッションはフィルタ後の記録を日時順に並べ、試合間隔が45分以上なら分割（画面で30/45/60/90分に変更可能）。フェーズが違う場合も分割。経過時間は最初から最後までのアップロード日時差で、ゲーム操作時間ではない。未取得・期間フィルタ・モード除外により実際の連続プレイと異なる可能性がある。同一秒の試合が複数ある場合は順序を断定せず連勝/連敗を算定しない。

同一キャラ・明示された同一フェーズ・ランクマッチで先頭/末尾の対戦前値が揃う場合だけ、その差を「参考」として表示する。末尾試合の結果が含まれないためセッション収支と同一視しない。unknownフェーズではこの参考差も算出しない。

相性は自分キャラ×相手キャラで集計。5試合未満は参考値として注意表示し、勝率順では後方へ並べる。実力差や収集範囲の偏りがあるため、キャラそのものの有利・不利は断定しない。

## ブラウザと容量

60秒自動更新・Safari復帰時・手動更新の既存タイミングで小さいindex/statusを確認。選択期間に必要な月だけ、ハッシュが変わった場合に月別JSONを取得する。未変更の月を毎分ダウンロードしない。通信失敗時は前回表示を保持する。試合一覧は20件ごとに表示、セッションは20件ずつ追加表示する。

最初の20件は約16KB（正規化後、インデント込み）。1試合約800バイトの仮定で100試合/日なら約2.4MB/月・約29MB/年。実際の件数・欠損に応じて変わる。月ファイルが1～2MBを超える場合は月内の不変チャンクへ分割し、indexのスキーマと読み込みを互換移行する。Gitコミット数・Pages転送量・iPad実機のDOM性能も監視する。現在の構成に有料サービスやDBは追加していない。
